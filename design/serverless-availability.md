# Serverless availability & booking — feasibility

**Question.** Publish a publicly reachable availability page, with a link that
creates a calendar appointment for both the requester and the owner, using
iCloud and a Hide My Email alias — with no central server, so nothing about the
owner's calendar passes through a third party.

**Short answer.** The valuable two-thirds works and nobody else offers it. The
last third — *instant, guaranteed booking* — is not achievable without a server,
and the reason is structural rather than a missing API. The honest product is a
**request page**, not a booking page, and that distinction should be in the UI
rather than buried.

---

## What does not work, with evidence

Two of the idea's load-bearing assumptions fail.

### iCloud cannot host the page

iCloud Drive public links are file-sharing links. They hand back the raw file or
a viewer chrome; they do not serve an HTML document as a rendered page at its own
URL. There is no "web hosting" surface in iCloud at all since iWeb/MobileMe
publishing was retired.

So "iCloud publishes a web page" is not a thing that exists. iCloud publishes a
**calendar feed**, which is a different and narrower object.

### A browser cannot read the iCloud feed

iCloud *can* publish a calendar publicly — Calendar → Share Calendar → Public
Calendar gives a `webcal://p##-calendars.icloud.com/published/2/…` URL serving
ICS. That part is real, free, requires no server, and cal-mirror already produces
exactly the right calendar to point at it.

But those endpoints send no `Access-Control-Allow-Origin` header, so page
JavaScript on any other origin cannot fetch them. Calendar feeds are consumed by
calendar clients, which are not bound by CORS; browsers are. Every workaround is
a proxy, and a proxy is a server.

**Consequence:** a page cannot render live availability pulled from iCloud.
Availability has to be **baked into the page when it is generated**, on the
owner's device.

### `mailto:` cannot carry an invitation

RFC 6068 defines `subject`, `body`, `cc` and friends. There is no attachment
mechanism, and clients ignore invented ones. So a link cannot hand someone a
`text/calendar` part — which is what an actual invitation is.

### Nothing can write to the owner's calendar unattended

Not a limitation to route around — it is the security model. Any design where a
stranger's click silently lands an event in your calendar requires something
holding a credential for your calendar. That something is a server, and its
existence is the thing this idea is trying to avoid.

## What does work

### 1. Availability, already built

Mirror the real calendars into a "Shared Availability" calendar, busy-only, with
`#nomirror` on anything private. That is today's product, unchanged. The output
is a calendar containing nothing but opaque blocks — safe to publish by
construction, which is the whole reason the busy-only projection exists.

### 2. Publishing, two grades

**Grade A — zero infrastructure.** Publish that calendar from iCloud. Anyone with
the link subscribes and sees your blocks, updating automatically. No server, no
page, no build step. Good for colleagues and family; useless to a stranger who
just wants to propose a time.

**Grade B — a static page, generated by the tool with everything baked in.**
cal-mirror writes ONE self-contained HTML file from the local calendar and the
owner serves it wherever they like.

Baking it in is not a workaround for CORS — it is the better design, for a
reason the rest of the product already turns on: **the owner can read the entire
artifact before publishing it.** Every byte a stranger can ever see is in one
file you can open in a text editor. That is a far stronger claim than "trust our
server", and it means "preview exactly what strangers will see" is a feature
rather than a promise.

A working prototype is in `design/prototype/` — 9 KB, and `grep` for `http`
finds no external URL of any kind. There is no
application server and no third party sees anything beyond what the owner chose
to publish, but there *is* a static host. GitHub Pages already serves this
project.

The page is a **snapshot**, regenerated on a schedule, because of the CORS
finding above. Freshness is a function of how often it regenerates, and the page
should say when it was generated rather than implying it is live.

### 3. Booking, via the requester's own client

This is the part that works better than expected, and it is the interesting idea.

The page builds an `.ics` in the browser — no network — and hands it over as a
`blob:` download:

```
METHOD:REQUEST
ORGANIZER;CN=Requester:mailto:them@example.com     ← they type this
ATTENDEE;RSVP=TRUE:mailto:x9f2@icloud.com          ← the owner's Hide My Email alias
DTSTART / DTEND                                    ← the slot they picked
SUMMARY / DESCRIPTION
```

The requester opens it. Their calendar client creates the event and, seeing an
attendee on an event they organise, sends the iTIP invitation itself. The owner
receives a genuine calendar invitation in Mail and accepts it, which is what puts
it in their calendar.

**No server participated.** The requester's own client did the sending, and the
owner's own acceptance did the writing. Both halves are actions by people who
already had the right to take them.

A plain `mailto:` link sits underneath as the universal fallback: prefilled
subject and body, no attachment, works everywhere.

### 4. Hide My Email

Works, with one caveat: aliases are created by hand in Settings (iCloud+
required). There is no public API to mint them programmatically — which does not
matter, because one alias is enough and it is a one-time setup step.

## The thing that cannot be fixed: double-booking

Two people can open the page at the same time and request the same slot. Without
a server there is no place to hold an atomic reservation, and the page is a
snapshot besides. This is not a gap in the design; it is what "no server" means.

**So do not build a booking page. Build a request page.** The owner accepts or
declines each invitation — which they were going to do anyway, because accepting
is what writes it to their calendar. Frame it as *"propose a time"*, show *"times
I'm usually free, as of 09:00 today"*, and the ambiguity disappears because
nothing ever claimed to be a confirmed booking.

Every competitor's booking page needs their server precisely to hold that
reservation. Trading instant confirmation for no server is a real trade, and it
is the same trade the rest of this product already makes.

---

## Why it is worth building anyway

`docs/vs/*` currently lists *"no booking or scheduling links"* as a permanent
weakness on all thirteen comparison pages, against tools charging $56.99/year
partly for that feature. This would convert it into a narrower, more interesting
sentence: no instant booking, but a request page nobody else can offer, because
everyone else's runs on a server that has read your calendar.

It is also the only feature on the roadmap that is *easier* because the product
is on-device, rather than harder.

## Open questions, in the order worth answering

0. **Already answered:** the page can be generated with no external requests and
   the browser can build a valid `METHOD:REQUEST` with the requester as
   `ORGANIZER` and the owner as a `NEEDS-ACTION` attendee. Verified against the
   prototype; `design/prototype/test-invite.ics` is a ready-made one.
1. **Does the requester's client actually send the invitation?** Apple Calendar
   and Outlook send iTIP when you add an attendee to an event you organise. What
   they do with a *downloaded* `METHOD:REQUEST` file is more variable — some
   create it silently and send nothing. **This is the one assumption that decides
   whether the design is elegant or merely adequate**, and it is a 20-minute test
   across Apple Mail, Gmail web, and Outlook. Do this before anything else.
2. **Where does the page live?** GitHub Pages is free and already in use, but
   makes the availability page public to anyone who guesses the URL. An
   unguessable path is the same security model as an iCloud published calendar,
   which is to say: adequate, and worth stating plainly rather than implying more.
3. **How does the page get there?** A cal-mirror export command, run on the
   schedule the owner picks. On iOS this is a Shortcut away, now that 1.4.1 has
   App Intents.
4. **What granularity?** Free/busy blocks are a projection of the mirror the owner
   already publishes, so the page should derive from the same calendar rather than
   inventing a second policy nobody can see.

## Recommendation

Answer question 1 first. If clients do send the invitation, this is a genuinely
differentiated feature that fits the product's architecture instead of fighting
it. If they do not, it degrades to a `mailto:` request page — still serverless,
still more than the competition offers on-device, but much less magic, and worth
knowing before any of it is designed.
